# 실제 SSH 반복 실패와 인증 성공을 로그·패킷으로 연결한 사례

검증일: 2026-10-11 (Asia/Seoul)

## 문제

SSH 로그의 반복 실패가 단순 사용자 실수인지, 추가 확인이 필요한 인증 흐름인지 구분하려면 실패 횟수 외에 성공 이벤트와 네트워크 근거를 함께 확인해야 한다. 이 사례는 동일 사용자·IP의 반복 실패 뒤 정상 인증이 발생하는 흐름을 일회성 Linux 실습에서 재현했다. 실제 운영 침해 사건이나 외부 서버 공격 사례가 아니다.

## 환경과 재현

GitHub Ubuntu 24.04.5 실행기, Python 3.14.8, OpenSSH_9.6p1 Ubuntu-3ubuntu13.19를 사용했다. 임시 키와 별도 설정으로 SSH 서버를 127.0.0.1:22222에만 열고, 잘못된 공개키로 5회 인증한 뒤 유효한 공개키로 1회 인증했다. 클라이언트는 원격에서 true 명령만 실행했다.

sshd의 출력은 일회성 systemd unit의 native journal에 기록했고, 같은 loopback 트래픽을 tcpdump로 캡처했다. 서버의 기본 SSH 설정과 사용자의 기존 authorized_keys는 건드리지 않았다. 실행 종료 시 자신이 만든 unit을 중지하고 임시 키를 삭제했다.

전체 절차는 [실습 실행기 안내](../labs/ssh/README.md)에 있다.

## 관측 결과

[성공한 원격 검사](https://github.com/honyeongs/friendly-octo-palm-tree/actions/runs/38100969246)에서 다음을 확인했다.

- 앞선 인증 5회의 클라이언트 종료 코드는 각각 255, 마지막 정상 인증의 종료 코드는 0이었다.
- 네이티브 journal에서 유효한 인증 실패 5개와 성공 1개를 읽었다.
- 같은 호스트·출발지 IP의 60초 이내 실패 5회 기준으로 의심 구간 1개가 생성됐다.
- 같은 사용자에 대한 반복 실패 뒤 300초 안의 첫 성공으로 인증 상관분석 1개가 생성됐다.
- 실제 캡처 패킷 151개를 읽고 TCP 연결 시도 6회 이상과 탐지 구간의 대응 패킷 근거를 확인했다.
- Windows/Linux, Python 3.11/3.14 테스트와 별도의 Chromium 브라우저 검사도 모두 통과했다.

캡처 패킷 수는 실행 환경과 SSH 세션 종료 시점에 따라 달라질 수 있으므로 정확히 151개를 회귀 테스트 조건으로 고정하지 않았다. 재현 성공 조건은 인증 이벤트 수와 결과, TCP 시도 수의 하한, 같은 시각 범위의 패킷 연결이다.

## 구현에서 다룬 문제

실제 공개키 인증 메시지는 지문 앞에 `ssh2:`가 붙는다. 텍스트 파서가 이 형식을 지원하고 journal의 마이크로초 시각을 UTC로 변환하도록 했다.

초기 실습에서 정상 공개키 인증이 거부되어 일회성 서버의 PAM 계정 검사를 활성화했다. 변경 후 정상 성공 이벤트를 생성했고, 그 성공을 기존 실패와 연결하는 전체 흐름이 통과했다. 비밀번호 인증은 계속 비활성화했다.

## 결과 해석과 한계

이 흐름은 '반복 실패 뒤 인증 성공'을 보여주며 계정 탈취를 증명하지 않는다. 실제 운영에서는 사용자 확인, 작업 시간, 자동화 변경, 인증키 관리 이력 등을 함께 검토해야 한다.

TCP 패킷은 연결 시도·응답·재전송의 근거를 제공한다. SSH 인증 내용은 암호화되므로 패킷에서 사용자나 성공 여부를 직접 추출하지 않았다. 호스트·서버 주소 매핑과 같은 출발지 IP·시각 범위로 연결했다.

loopback의 단일 사용자·서버 실습은 NAT, 공유 IP, 다중 호스트, 시각 오차, 대규모 운영 부하를 검증하지 않는다. 그 부분은 단위 테스트와 별도의 운영 데이터 검증을 구분해야 한다.

## 공개한 자료

Git에는 구현·재현 실행기·합성 샘플만 포함한다. Actions에는 사례 요약 case.json, 분석 결과 report.json, tcpdump 통계 로그를 보관했다. 실제 원본 journal과 PCAP, 개인키는 게시하지 않았다. 첫 화면과 samples 폴더의 데이터는 합성 데이터임을 명시했다.
