# 운영 앱 이후의 우선순위

## 지금 이어서 완료한 운영 준비

- 재시작해도 계정·사건·조사 메모·전송 대기가 남는 저장소.
- 조직 간 조회·수정 차단, 관리자/분석가/조회자 역할, CSRF·Origin·Host 검사.
- 비밀 정보를 응답 오류·감사·외부 알림에 넣지 않는 입력/출력 경계.
- 샘플 앱의 실제 실패 5회와 성공 1회가 탐지로 이어지는 브라우저 검사.
- 백업 무결성 확인·복구 절차, 기본 30일 정리, 관리자 비밀번호 복구 명령.
- Windows 실행기, 외부 키를 비워 둔 설정, 연결/운영/사용자 작업 문서.

## 다음에 먼저 할 일: 제한된 시범 운영

관리하는 서버 1대와 앱 1개를 연결하고 조직 사용자 2~3명으로 시작합니다. 운영자가 실제 수집 IP·시간대·계정 식별자가 맞는지 확인하고, 정상 사용자의 실패가 얼마나 탐지되는지 조사합니다. 탐지를 무조건 줄이지 말고 소스별 정상 패턴·서비스 중요도를 기록합니다. SMTP/웹훅을 쓴다면 실제 알림 도착과 중복 처리를 확인합니다. 일주일 단위로 누락·오탐·처리 시간·큐 적체·디스크 사용량을 기록한 뒤 탐지 기준을 조정합니다.

## 다음 코드 확장 후보

1. 회사 계정으로 로그인: 기존 인증 제공자의 OIDC/SSO와 MFA 연결. 제공자 도메인·클라이언트 등록·비밀은 조직에서 준비해야 합니다.
2. 조직별 외부 알림 비밀 분리: 현재 운영자 공통 웹훅 대신 조직별 비밀 관리 도구와 수신처. 고객 간 알림 경계 검증 포함.
3. 지속 수집 강화: journal 커서 직접 구독, 로그 회전·재부팅·지연 이벤트 처리, 큐 적체 경보. 지금의 파일 폴링을 교체하되 SDK 재전송 계약은 유지.
4. 규모 확장: 실제 부하 측정 후 PostgreSQL과 독립 작업 큐로 이전. 스키마 마이그레이션·조직 격리·중복 방지·재처리 테스트를 먼저 준비.
5. 탐지 확대: 여러 계정 대상 실패, 여러 IP 대상 같은 계정 실패, 관리자 권한 변경과 로그인 연계. 위험도와 정상 대조군을 먼저 정의.
6. 외부 시스템 연계: 회사가 쓰는 SIEM/OpenTelemetry와 이벤트 변환, 티켓 시스템과 사건 상태 동기화. OTLP를 지원한다고 단정하지 말고 실제 인터페이스를 추가·검증.

SSO·인프라·알림 수신처를 임의로 생성하거나 유료 서비스에 가입하지 않았습니다. 현재 로컬 시범 운영과 이후 상용 배포 검증은 구분합니다.
