# 확장 구현 상태와 다음 아이디어

2026-10-11 사용자가 4단계 전체 구현과 GitHub 업로드를 승인했다. 아래 1~4단계의 코드, 샘플, 테스트와 실행 절차를 구현했다. 실제 Linux 실습·CI의 실행 상태는 VERIFICATION.md와 해당 GitHub Actions 실행 결과를 구분해서 확인한다. 아래 설명은 각 기능의 설계 목적과 완료 기준이다.

## 1. 실제 Linux SSH 로그 검증: 가장 먼저 추천

목적은 합성 데이터로 만든 파서와 탐지가 실제 환경에서도 맞는지 확인하는 것이다. 로컬 VM의 journald에서 시간대와 연도가 보존된 로그를 추출하고, 서버 버전과 인증 설정을 기록한다. 먼저 수동 인증의 실패·성공 사례로 검증한다.

실제 메시지와 현재 지원 형식이 다르면 parsers 아래에 journald JSON 파서를 추가해 같은 AuthEvent로 변환한다. 기존 텍스트 파서를 함께 유지한다.

완료 기준: 환경 구성 방법, 재현 절차, 익명화한 이벤트, 기대 결과, 분석 보고서가 하나의 사례 문서로 연결된다. 탐지 건수뿐 아니라 미해석·오탐 사례를 기록한다. 공개 자료에는 실제 운영 계정·주소를 넣지 않는다.

## 2. 반복 실패 직후 성공한 인증 연결: 가장 효과적인 기능 확장

목적은 반복 실패 가운데 추가 확인이 필요한 사례를 구분하는 것이다. detectors 아래에 별도 상관분석 규칙을 추가하고 기존 반복 실패 규칙을 재사용한다.

같은 호스트·출발지 IP·대상 사용자의 실패 뒤 일정 시간 내 성공이 있었는지 찾는다. 보고서에는 실패 구간과 성공 이벤트의 줄 번호, 사용자, 시간 차이를 함께 넣는다. '침입 성공' 대신 '반복 실패 이후 인증 성공'으로 표현한다.

완료 기준: 같은 IP라도 사용자가 다른 사례, 성공이 먼저 있었던 사례, 시간 경계, 공유 IP에 따른 오탐을 테스트한다. 성공 이벤트의 존재만으로 침입을 단정하지 않는 해석을 문서화한다.

## 3. 저장된 패킷과 SSH 로그 비교: 네트워크 역량 강화

로컬 실습에서 저장한 PCAP/PCAPNG를 검증된 분석 엔진으로 읽고 TCP 연결 실패·반복 연결 통계를 추출한다. 도구 자체에서 TCP 프로토콜 파서를 새로 만들지 않는다.

같은 대상 서버·출발지 IP·시간대의 로그와 연결해 'TCP 연결 시도 → SSH 인증 실패 → 인증 성공 여부'를 비교한다. SSH 암호화 패킷만으로 사용자 이름이나 인증 실패를 직접 알아낼 수 있다고 가정하지 않는다.

완료 기준: 동일 실습의 로그와 패킷에서 시각을 정렬하고, 연결되지 않는 원인과 암호화 때문에 확인할 수 없는 내용을 설명한다. 패킷 분석 의존성은 선택 설치 항목으로 분리한다.

## 4. JSON 결과 비교 화면: 시연 편의 개선

두 분석 결과를 열어 IP별 실패 횟수, 사용자, 시간 구간, 근거를 비교한다. 먼저 로컬 JSON을 읽는 화면으로 시작하고 인증·서버 저장 기능은 필요가 생겼을 때 추가한다.

완료 기준: 결과 선택 → 의심 구간 선택 → 근거 확인 → 다른 결과와 비교가 끊기지 않는다. UTC와 사용자 표시 시간대를 구분하고, 합계와 이동 구간 최대값을 혼동하지 않도록 표시한다.

## 5. 처리 규모와 공급망 검증 개선

더 큰 파일이 필요해지면 입력 시각 정렬 보장을 전제로 스트리밍 처리와 상태 만료를 구현한다. 입력이 뒤섞인 경우의 정책과 중복 로그 식별 기준도 별도로 정한다. 먼저 파일 크기별 메모리·실행 시간을 측정하고 현재 구현과 결과가 같음을 검증한다.

공유 환경에서 사용하게 되면 GitHub Actions 참조를 검증된 커밋 SHA로 고정하고 자동 업데이트를 연결한다. 라이선스 선택과 배포 패키지 검증도 공개 배포 단계에서 결정한다.
