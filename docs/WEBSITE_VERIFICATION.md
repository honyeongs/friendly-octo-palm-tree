## 실제 공개 주소 브라우저 검증

로그인하지 않은 새 Chromium 컨텍스트에서 아래 10개 검증이 모두 통과했습니다.
로컬 빌드에서도 같은 흐름을 확인했습니다.

1. 브라우저 안에서 파일/로그 분석 완료.
2. 원본 Python CLI 결과와 웹 결과 일치, 입력별 경계 검사.
3. Worker 취소 후 다시 준비·분석 가능.
4. PWA manifest의 standalone·scope·192/512px 아이콘 확인.
5. Windows `.url` 바로가기 다운로드 및 실제 공개 URL 확인.
6. 1440px 데스크톱과 390/360px 모바일에서 페이지 가로 넘침·도구 메뉴 배치 검사.
7. 설치 버튼/안내 연결 확인.
8. 공개 앱 자산 준비 후 네트워크를 끊고 새로고침·분석 재실행.
9. 세션 지우기 후 이전 사용자 입력·보고서가 복원되지 않음.
10. 분석 중 원본 파일/로그의 서버 전송, 외부 앱 요청과 pageerror가 발생하지 않음.

네트워크 검사는 앱 요청의 메서드·대상과 캐시 목록을 관찰했습니다.
호스팅 제공자의 일반 접속 기록·플랫폼 스크립트까지 통제하거나 OS의 물리 메모리 삭제를 보증하는 검사는 아닙니다.
일부 환경에서 호스팅 제공자가 삽입하는 인라인 보안 스크립트가 앱 CSP에 차단되는 콘솔 알림이 관찰됐습니다.
이를 허용하기 위해 `unsafe-inline`을 추가하지 않았으며, 위 실제 분석 흐름은 통과했습니다.
현재 Sites 정적 호스팅에서는 생성된 `_headers`의 CSP/X-Frame-Options가 HTTP 응답에 적용되지 않는 것도 확인했습니다.
주 문서의 meta CSP는 동작하지만 Worker의 응답 CSP·frame-ancestors 보호와 같다고 주장하지 않습니다.
별도 서버/인증 서비스를 붙이는 상용 배포에서는 응답 헤더를 제어할 수 있는 게이트웨이 구성이 추가로 필요합니다.

## 해석과 한계

- Windows OS에 실제 설치·시작 메뉴/바탕화면 아이콘 생성은 자동 수행하지 않았습니다. 설치 확인은 사용자가 브라우저에서 직접 해야 합니다.
- `.url`은 인터넷 바로가기이며 서명된 EXE/MSIX 설치 프로그램이 아닙니다.
- 실제 개인 PC Sysmon 수집이나 실제 악성코드 실행 검증이 아닙니다.
- NetSec의 공개 웹은 SSH/PCAP 오프라인 분석용입니다. 기존 로컬 SaaS의 로그인·청구·조직 DB 운영은 인터넷 서비스로 노출하지 않았습니다.
- 호스팅 방화벽·접속 정책·브라우저 저장 공간·네트워크 상태에 따라 실패할 수 있습니다. 상용 SLA·무결점·안전 인증을 주장하지 않습니다.
- GitHub CI는 이 기록과 별도로 각 커밋에서 실행됩니다. 로컬 통과를 원격 CI 통과로 대신 표기하지 않습니다.
